# Issue #30 — overview.md

## 目的
'month' ビューで、**フルデイイベント（日を跨ぐ・1 日いっぱいのイベント）** と **時間ごとのイベント** を区別し、後者が誤ってリサイズ / 移動されて 'week' ビューの `.rbc-row`（上部バンド）に落ちてしまう事故を防ぐ。

前提の区別方法（Issue #29 で整備済み）:
- フルデイイベント = `start_time: 0:00 / end_time: 当日 23:59` → `allDayAccessor(event)` が `true` → `.rbc-event-allday` クラス付与 + 週ビューの `.rbc-row` 配置
- 時間ごとのイベント = それ以外（例: 9:00–10:00）→ `.rbc-event-allday` クラスなし

## ユーザーストーリー
- **対策 1**: タイムテーブルの 'month' ビューで、フルデイイベントがデフォルト色 `#3174ad` と見分けがつく別の色（赤・紫系統を避け、白文字が読める濃色）で表示され、一目で「フルデイイベントかどうか」が分かる
- **対策 2**: 'month' ビューで時間ごとのイベントを掴んで、リサイズが効かない（伸縮不可）。誤ってリサイズし、"week の時間列のイベント"がバンド行に移る事故が起きない
- **対策 3**: 'month' ビューでフルデイイベントをリサイズする際、隣のセルに別イベントがあっても、EW（横）リサイズハンドルを確実に掴める
- どの対策も 'week' ビューのドラッグ・アンド・ドロップ動作には支障を出さない

## スコープ
### 実装するもの
- 対策 1: フルデイイベントの色分け（`.rbc-event-allday` を CSS で着色）
- 対策 2: 'month' ビューでの時間イベントへの DnD 無効化（`draggableAccessor` / `resizableAccessor`）
- 対策 3: EW リサイズアンカーのヒット領域拡大 + z-index（CSS）
- 現行 `eventPropGetter` の削除・整理

### 対象外
- DnD 操作の `start_time` / `end_time` 反映
- 対策 2 の確認ダイアログ方式と、週ビュー `.rbc-row` へ移す処理（Issue #31）
- バックエンド・DB 変更

## リスク・トレードオフ・未解決点
1. **`draggableAccessor` / `resizableAccessor` の導入**（最重要）
   - accessor は純関数として振る舞う。`currentView` を closure で参照するため、ビュー切替でアクセサが作り直される（再レンダーが 1 回増えるだけ）。イベントループ等の副作用はない
   - 'month' でのみ時間イベントを無効化するので、'week' の時間列リサイズ（縦）には影響しない
2. **`eventPropGetter` の削除**
   - 現行実装は `state` が自分のイベントのみにフィルタ済み（`CalendarView.tsx:31-33`）なため、else 分岐が実効しない + `pointerEvents: 'auto'` は既定値の no-op。削除しても挙動は変わらない（要調査項目への回答）
   - 万一「自分のイベント以外を半透明化」等の意図が残るなら、別の手段（`eventPropGetter` で `opacity` を指定）で実現可能だが、現状 filter により不要
3. **対策 3 の CSS 変更は実ブラウザ確認が必須**
   - EW アンカーのヒット領域・z-index の調整は、星っぽい相互作用（隣イベントとの重なり方）に依存。テストコードでは検証しきれないため、実ブラウザで受け入れ要件を確認する（test-plan.md 参照）
   - アンカーを広げすぎると、クリック操作（イベント選択）を邪魔する可能性 → 値は実ブラウザで調整
4. **色の選択は UX 判断** — 赤・紫系統（マイルストーン色 `#9c27b0` など）を避け、`#3174ad` と区別でき、白抜き文字が読める濃色を選ぶ。本計画は候補 `#00695c`（Teal 800）を提示。実行時にユーザーと最終確認
5. **フルデイ判定の曖昧さ** — `isFullDayEvent` が `0:00–23:59` をフルデイとみなす既存仕様に依存。手作りで丁度 `0:00–23:59` のイベントは無効化対象になるが、実用上は望ましい挙動
